# Technical Inspection Report — ML-Based Offline Log Monitoring for Air-Gapped Networks

Prepared: 2026-09-17
Scope: Full repository inspection only. **No files modified.**

---

## 1. Current Architecture

Layered monolith, Python 3.11+ (type hints throughout), no framework beyond Streamlit UI.

```
data/logs (sample CSVs/TXT/LOG/JSON?)  →  src/ingestion.py  (files + uploads)
                                          src/windows_event_ingest.py  (Windows Event logs)
        ↓
src/preprocessing.py        cleaning / normalization / dedup
        ↓
src/feature_engineering.py  ~39 hand-crafted numeric features
        ↓
src/model.py                IsolationForest | OneClassSVM  → anomaly_score (min-max normalized)
        ↓
src/severity.py             assign_severity()  (thresholds 0.3/0.6/0.8 → Low/Med/High/Crit)
        ↓
backend/risk.py             build_risk_scores()  statistical + rules + weights → risk 0–100,
                            OVERWRITES severity using boundary map 24/49/74/100
        ↓
backend/explanations.py     machine explanation string
        ↓
backend/pipeline.py         run_pipeline() → bundle; persists top-50 alerts to SQLite
        ↓
app/dashboard.py  (Streamlit, 4 tabs)      backend/reporting.py  (CSV/PDF)
```

Layers: `src/` (core processing), `backend/` (orchestration/reporting/persistence), `app/` (UI), `frontend/` (alias re-export), `config/`, `data/`, `tests/`, `experiments/` (**absent**).

## 2. Current Data Flow

1. `main.py` CLI → `backend.pipeline.run_pipeline_on_paths()` → `collect_from_paths()` → `run_pipeline()`, writes CSV+PDF to `reports/`.
2. `run_backend_demo.py` — same pipeline, prints summary/alerts.
3. Dashboard (`app/dashboard.py`) — **separate, parallel path**: upload or Windows collection → `preprocess_logs()` → `build_features()` → `LogAnomalyModel.fit_predict()` → `assign_severity()`. **Does NOT call risk, rules, explanations, or the DB.**
4. `src/windows_event_ingest.py` — priority: hard-coded admin CSV → pywin32 → wevtutil.
5. `backend/log_parser.py` — regex parsers exist but are **not wired into the pipeline**.

**Consequence:** Backend and UI produce different features, severities, and columns for identical input. Reports generated by CLI contain `risk_score`/`explanation`; dashboard output does not.

## 3. Current ML Pipeline

- `LogAnomalyModel` (src/model.py): sklearn Pipeline [StandardScaler → IsolationForest(300 trees) **or** OneClassSVM(rbf, nu=contamination)].
- Fits and predicts on the **same data** (no split, no validation). `contamination` default 0.12, hard-linked to severity via min-max normalization per batch.
- `_normalize_scores()`: min-max per batch → the *same log line scores differently depending on unrelated rows in the batch*.
- Hybrid scoring exists (`risk.py`) but is broken/unused by UI (see §7).
- No model persistence, no metadata, no evaluation, no training/validation split, no OCSVM score normalization sanity check.

## 4. Current Frontend (Streamlit)

Single page `app/dashboard.py`; `frontend/dashboard.py` is a pure re-export alias.

- Sidebar: input mode (Upload | Windows Event Logs), engine select, contamination slider, "Enable offline monitoring" checkbox (flag-only).
- Tabs: Overview (2 charts + timeline), Alerts, Processed Records + CSV/PDF download buttons.
- No navigation/pages, no alert lifecycle actions, no live monitoring view, no config UI, no audit UI, no model evaluation UI, no pagination (loads full frame into memory).

## 5. Current Database

SQLite `data/monitoring.db`.

- Tables: `alerts` (10 cols), `application_settings` (key/value). Only `alerts` actually written (top-50 per run, `INSERT OR REPLACE` keyed by `alert-{row_index}` → ID collisions across runs).
- `list_alerts()` exists but is never called by UI.
- No `events`, `analysis_runs`, `alert_history`, `rules`, `model_metadata`, `monitoring_sources`, `audit_logs`, **no indexes** beyond implicit PK.

## 6. Current Features

- **Feature engineering (src/feature_engineering.py):** ~39 features: message length/counts, unique words, digits/alpha/uppercase/punctuation/symbol counts, keyword counts (alert/security/network/system/web/AWS), exclamation/question marks, IP presence/frequency, error-code/http-status flags, login/failed-login flags, request verb, path tokens, keyword density, digit:alpha ratio, timestamp-known, hour/weekday/business-hours/weekend, source event count/density, hour event count, source-kind (linux/windows/web/cloud).
- **Severity:** Low/Medium/High/Critical with two competing threshold sets.
- **Rules:** config-driven rule engine (broken — §7).
- **Detection:** IF, OCSVM, a naive statistical score (`statistical.py`: reuses ml score + failed-login + word-count ratios), rule weight.
- **Reporting:** CSV + minimal PDF (summary + top-10 rows).
- **Audit:** JSONL audit log (`logs/audit.log`) written by dashboard and nothing else.

## 10. Security Issues

- S1 **Rule engine uses `eval()`** on config strings (even whitelisted, unsafe/fragile pattern) — required replacement with restricted AST/declarative evaluator.
- S2 No upload size enforcement despite `max_upload_size_mb` existing; no filename/path protections for monitoring dirs.
- S3 Malformed CSV/JSON crashes batch; no isolation, no warnings.
- S4 Text read with `errors="ignore"` silently drops data (evidence integrity).
- S5 Log content never executed (good) — but `start ... powershell.exe -File ...` shell-launch uses an absolute, machine-specific script path.
- S6 Absolute hard-coded paths: `C:\Users\Lenovo\Desktop\ml log analysis\...` in `collect_windows_logs.ps1:6`, `ADMIN_CSV_PATH` in `windows_event_ingest.py:12`, `tmp_collect_wev.py:5`.

## 11. Performance Issues

- CSV parsed with slow `engine="python"` (the 611 KB `windows_events_admin.csv`); no chunking for 500 K+ rows.
- Model retrained every Streamlit rerun; no `st.cache_data`/`st.cache_resource`.
- Full frame loaded into Streamlit with no pagination.
- `IsolationForest(n_jobs=-1, n_estimators=300)` refit per batch — expensive for a watcher-driven incremental flow.
- `reporting.py` builds full CSV string in memory.
- No benchmarks, no memory/latency measurement.

## 16. Risk of Each Change

| Change | Blast radius | Reversibility | Key risk / mitigation |
|---|---|---|---|
| Rule engine rewrite | Backend.risk, pipeline, tests | High (pure function, unit-tested) | New evaluator must preserve scalar+row semantics — covered by regression tests incl. `>=`/`<=`/`!=` |
| Failed-login aggregation | feature_engineering, statistical, rules, tests | Medium (can gate behind config) | Existing feature names reused → model behavior shifts; keep old columns additive, default window configurable |
| Unified risk/severity | severity.py, risk.py, pipeline, dashboard, DB, reports | Medium | CLI output changes; single-source-of-truth guarantees consistency — snapshot reports before/after |
| Dashboard→`run_pipeline` parity | app/dashboard.py | High | Feature-parity risk (dashboard loses columns); mitigate by keeping all `PipelineBundle` frames exposed |
| DB schema migration | database.py, pipeline, dashboard | Medium | Old `monitoring.db` incompatible → recreate + migrate alerts; keep `insert_alert` API for compatibility |
| Real monitoring (watchdog/offsets) | new files + dashboard LIVE page + DB | High (new code path) | Offset/rotation races; process whole file once on enable; checkpoint after each successful chunk; test with synthetic appends |
| Modular parsers | log_parser→parsers/, ingestion, pipeline | Medium | Regressions on existing sample formats → keep golden-sample parser tests |
| Common schema | preprocessing, parsers, features | Medium | Column renames ripple through FEATURE_COLUMNS/tests — schema adapter keeps old columns visible |
| Statistical/threshold/fusion rewrite | risk.py, statistical.py, new files | High | Threshold drift — fallback documented; eval A–D against synthetic labelled data |
| Evaluation/benchmark/model manager | new files, models/ dir | High | Never fabricate metrics; clearly mark unlabelled datasets; store experiment JSON locally |
| Reporting/audit/timezone | reporting.py, audit.py | High | Cosmetic-regression low; keep `export_csv_bytes` signature |
| `.gitignore` + removals | repo hygiene | High | Only removes dead/regenerable files |
| Performance (C engine, chunking, caching) | ingestion, dashboard | High | Streamlit cache semantics — cache on (file identity + params), never cache mutable DB state |

**Highest-risk items overall:** DB schema migration (P0-6) and real file monitoring with offsets (P1-8); both are isolated to new code + tests before being exposed in the UI.
